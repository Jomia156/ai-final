## Ручное тестирование

Запустите приложение с помощью `docker compose up --build`. Для всех примеров используется один и тот же текст, чтобы избежать кеш-ключей.

### Сценарий 1: Успешная суммаризация

Убедитесь, что в `.env` установлены рабочие значения `APP_LLM_API_KEY`, `APP_LLM_BASE_URL` и `APP_LLM_MODEL`, затем выполните curl-запрос из основного README. Ожидаемые результаты:
- HTTP статус: 200
- `source`: `"llm"`
- `cached`: `false`

### Сценарий 2: Проверка валидации

```bash
curl -i http://localhost:8000/v1/summaries \
  -H 'Content-Type: application/json' \
  -d '{\"text\":\"коротко\"}'
```

Ожидаемый результат:
- HTTP статус: 422
- Сообщение об ошибке указывает на нарушение минимальной длины текста

### Сценарий 3: Обработка недоступности модели

Очистите значение `APP_LLM_API_KEY` в файле `.env` и перезагрузите контейнер:

```bash
docker compose up --build
```

Отправьте валидный запрос и проверьте результат:
- HTTP статус: 503
- `source`: `"fallback"`
- `cached`: `false`
- Поле `summary` содержит первые предложения исходного текста
- В логах приложения видна метка `summary_degraded`
- Исходный текст и конфиденциальные данные не отображаются в логах

### Сценарий 4: Проверка механизма кеширования

Восстановите рабочий `APP_LLM_API_KEY` и отправьте два одинаковых валидных запроса:
- Первый ответ: `cached: false` (новый вызов модели)
- Второй ответ: `cached: true` (результат из памяти)
- В логах второго запроса: метка `cache_hit` без нового обращения к модели
